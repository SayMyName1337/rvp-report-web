# Руководство по развёртыванию и сопровождению

Информационная система «Суточный рапорт». ООО «СК Русвьетпетро».
Редакция от 15.09.2026.

Документ определяет порядок установки системы на сервер, ввода
её в эксплуатацию, резервного копирования, обновления и устранения
неисправностей. Документ рассчитан на администратора системы.

## 1. Требования к техническим и программным средствам

| Параметр | Значение |
|---|---|
| Операционная система | Linux |
| Процессор | не менее 2 ядер |
| Оперативная память | не менее 4 ГБ |
| Дисковое пространство | не менее 40 ГБ |
| Системное ПО | Docker версии 24 и выше с модулем Compose |
| Сертификат | сертификат TLS на имя узла (допускается сертификат внутреннего удостоверяющего центра) |
| Доступ | доступ к репозиторию исходного кода |

Ожидаемый объём данных составляет около ста тысяч строк базы данных
и около ста мегабайт файлов рапортов в год. Указанного дискового
пространства достаточно на несколько лет эксплуатации с учётом
резервных копий.

## 2. Порядок установки

### 2.1. Размещение исходного кода

```bash
sudo mkdir -p /opt/rvp-report && sudo chown "$USER" /opt/rvp-report
git clone <адрес репозитория> /opt/rvp-report
cd /opt/rvp-report
```

### 2.2. Настройка параметров среды

```bash
cp .env.example .env
```

В файле `.env` подлежат заполнению следующие параметры:

| Переменная | Значение |
|---|---|
| `DJANGO_SETTINGS_MODULE` | `config.settings.prod` |
| `DJANGO_SECRET_KEY` | случайная строка, порядок получения приведён ниже |
| `DJANGO_ALLOWED_HOSTS` | имя узла, например `rapport.company.ru` |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | `https://rapport.company.ru` |
| `POSTGRES_DB`, `POSTGRES_USER` | `rvp`, `rvp` |
| `POSTGRES_PASSWORD` | случайный пароль |
| `WITH_PDF` | `1` — с поддержкой выгрузки в PDF, `0` — без неё |

Ключ и пароль формируются командой:

```bash
python3 -c "import secrets; print(secrets.token_urlsafe(64))"
```

Файл `.env` содержит пароли, в систему контроля версий не помещается
и подлежит ограничению прав доступа:

```bash
chmod 600 .env
```

### 2.3. Размещение сертификата

```bash
mkdir -p deploy/tls
cp <файл сертификата> deploy/tls/server.crt
cp <файл закрытого ключа> deploy/tls/server.key
chmod 600 deploy/tls/server.key
```

### 2.4. Запуск

```bash
docker compose -f deploy/compose.yaml --env-file .env up -d --build
```

Первая сборка образа выполняется на самом узле и её
продолжительность определяется его мощностью: на узле с одним
процессорным ядром сборка с поддержкой PDF занимает около получаса,
на узле, соответствующем требованиям раздела 1, — несколько минут.
Последующие сборки используют кеш и проходят заметно быстрее.

Размер образа без средств преобразования в PDF составляет около
575 МБ, с ними — около 1,1 ГБ.

Данные в образ не включаются; за это отвечает файл `.dockerignore`.
Образ содержит только исходный код; файлы рапортов и хранилище
подключаются томами. Существенное увеличение времени сборки является
признаком попадания посторонних файлов в контекст сборки и требует
проверки указанного файла.

При запуске служба приложения последовательно выполняет применение
миграций, сборку статических файлов и создание групп ролей. Контроль
выполняется командами:

```bash
docker compose -f deploy/compose.yaml --env-file .env ps
docker compose -f deploy/compose.yaml --env-file .env logs -f web
```

### 2.5. Создание учётной записи администратора

```bash
docker compose -f deploy/compose.yaml --env-file .env \
    run --rm web manage createsuperuser
```

Пароль назначается лицом, выполняющим установку. Хранение паролей
в исходном коде, файлах настроек и переменных среды не допускается.

### 2.6. Предоставление доступа пользователям

Учётные записи создаются в панели управления по адресу
`https://<имя узла>/admin/`. Каждому работнику создаётся персональная
учётная запись; использование общих учётных записей не допускается,
так как при этом теряется возможность установить, кем выполнена
загрузка или замена данных.

Права определяются включением в группу:

| Группа | Должностное соответствие |
|---|---|
| Администраторы | сопровождение системы |
| Руководство | главный инженер и выше |
| Работники промысла | начальник ЦИТУ и его заместитель |

Группа «Работники промысла» подлежит назначению не менее чем двум
пользователям. При наличии единственного уполномоченного пользователя
его отсутствие приводит к пропускам в данных, нарушающим
сопоставимость сводок за период.

### 2.7. Загрузка ранее накопленных рапортов

При наличии рапортов за прошедшие периоды они подлежат загрузке
до начала эксплуатации: сводные показатели и дашборд рассчитываются
на основании накопленных данных.

```bash
docker compose -f deploy/compose.yaml --env-file .env \
    run --rm -v /путь/к/рапортам:/data web manage load_reports /data
```

После загрузки выполняется сопоставление наименований справочников.
Неизвестные наименования месторождений создаются автоматически
и отмечаются как требующие проверки.

```bash
docker compose -f deploy/compose.yaml --env-file .env \
    run --rm web manage link_aliases          # вывод предположений
docker compose -f deploy/compose.yaml --env-file .env \
    run --rm web manage link_aliases --apply  # применение
```

После применения синонимов рапорты подлежат повторной загрузке;
команда выводит соответствующее указание.

### 2.8. Включение HSTS

Заголовок HSTS включается только после подтверждения устойчивой
работы сертификата. Заголовок предписывает браузеру обращаться
к узлу исключительно по защищённому протоколу в течение заданного
срока; при ошибочном включении доступ к системе оказывается закрыт
на весь этот срок.

В файле `.env`:

```
DJANGO_HSTS_SECONDS=31536000
```

После изменения выполняется перезапуск службы `web`.

## 3. Резервное копирование

Копирование выполняется сценарием `deploy/backup.sh` по расписанию.
Копируются база данных и хранилище файлов; копии со сроком хранения
свыше установленного удаляются автоматически. Каталог размещения
задаётся переменной `BACKUP_DIR`, срок хранения — `BACKUP_KEEP_DAYS`.

```bash
crontab -e
```

```
0 3 * * * /opt/rvp-report/deploy/backup.sh >> /var/log/rvp-backup.log 2>&1
```

### 3.1. Восстановление

```bash
# база данных
docker compose -f deploy/compose.yaml --env-file .env exec -T db \
    pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists \
    < deploy/backup/db_2026-09-11_0300.dump

# файлы
docker compose -f deploy/compose.yaml --env-file .env \
    run --rm -v "$PWD/deploy/backup:/backup" web \
    tar xzf /backup/media_2026-09-11_0300.tar.gz -C /app/media
```

Проверка восстановления выполняется на отдельном узле не реже одного
раза в квартал. Резервная копия, восстановление из которой
не проверялось, не может считаться резервной копией.

## 4. Обновление

```bash
cd /opt/rvp-report
git pull
docker compose -f deploy/compose.yaml --env-file .env up -d --build
```

Миграции применяются при запуске. Перед обновлением выполняется
резервное копирование:

```bash
./deploy/backup.sh
```

## 5. Эксплуатация

Фоновые задачи в системе отсутствуют: разбор рапорта и формирование
презентации выполняются в рамках обработки запроса. Сведения
о результате загрузки выводятся в протоколе разбора; подробности
регистрируются в журнале приложения:

```bash
docker compose -f deploy/compose.yaml --env-file .env logs -f web
```

Сопоставление смежных суток выполняется при загрузке. Повторный
расчёт за произвольный интервал дат:

```bash
docker compose -f deploy/compose.yaml --env-file .env \
    run --rm web manage crosscheck --from 2026-08-01 --to 2026-08-31
```

## 6. Устранение неисправностей

Сообщения об ошибках содержат сведения о характере неисправности
и рекомендуемых действиях. Код сообщения, названный пользователем,
определяет источник неисправности.

| Признак | Проверяемый источник |
|---|---|
| Страница не открывается | журнал службы `nginx`, сертификат в каталоге `deploy/tls` |
| «Приложение сейчас недоступно» (502) | служба `web` не запущена либо завершилась аварийно; журнал службы `web` |
| «Сбой в приложении» (500) | журнал службы `web` за время, указанное пользователем |
| «Эта страница не для вашей должности» (403) | состав групп учётной записи пользователя |
| Рапорт загружен, данные отсутствуют | протокол разбора на странице загрузки, затем журнал службы `web` |
| Разбор использует неверные ячейки | раздел «Разметка» интерфейса системы |
| Сводка меньше ожидаемой | сведения о полноте данных на странице сводки |
| Выгрузка в PDF недоступна | сборка образа выполнена с параметром `WITH_PDF=0` |

## 7. Сведения для службы информационной безопасности

- **Обращение к внешним сетям не производится.** Зависимости
  устанавливаются на этапе сборки образа, библиотека построения
  графиков включена в состав исходного кода, внешние сети доставки
  содержимого не используются.
- **Исполняемый код в данных отсутствует.** Обрабатываются файлы
  формата `.xlsx`, формируются файлы `.pptx` — форматы, не содержащие
  макросов. Загружаемые файлы проверяются по расширению, сигнатуре,
  размеру и структуре.
- **Персональные данные в базу данных не помещаются.** Не сохраняются
  ни текст обращений в здравпункт, ни описание происшествия.
- **Файлы не отдаются веб-сервером напрямую.** Выгрузка выполняется
  через представление с проверкой прав доступа и регистрацией
  в журнале выдач.
- **Приложение выполняется не от имени суперпользователя** внутри
  контейнера.
- **Сетевой доступ извне имеет только служба `nginx`.** Порт базы
  данных не публикуется.
